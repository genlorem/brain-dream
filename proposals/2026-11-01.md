## Proposal #1: Семантический dedup кандидатов вместо точного sha256

**Что заметил:** сон 2026-10-31 прямо называет корень: «Генератор инсайтов не сверяется с уже найденным — один пробел vipzal-admin переоткрыт 8 раз». `content_hash_insight()` в `lib/content-hash.sh` хеширует только lowercase + collapse-whitespace нормализацию — точное совпадение текста. Линзы (problem/risk/opportunity/practice) и разные Sonnet/Gemini-проходы формулируют один и тот же пробел разными словами → разный sha256 → `registry_has_hash` его не видит, `hit_count`/`confidence` не растут, кандидат «открывается» заново. При этом `candidate_count` держится стабильно 144-159/ночь при 60 Sonnet-вызовах — нет признака, что внутриночной dedup вообще снижает приток.

**Предложение:** в `lib/insight-hashes.sh` добавить вторичную проверку через embedding-similarity, используя уже существующий в репо fastembed-инструмент (`tools/finding-dedup.py`, упомянут в коммите `11861d3`/`883234a` для session-observer) — за флагом `DREAM_DEDUP_SEMANTIC` (default 0), с тем же `nice -n 19 ionice -c 3` + `ccwork.slice CPUQuota=200%` ограничением, что уже стоит на `session-observer-cron.sh`, т.к. fastembed ранее давал load 22-25.

**Обоснование:** закрывает ровно ту причину, которую нашёл сам сон, а не общую «dedup слабый». Переиспользует готовый инструмент вместо нового.

**Риск:** средний (CPU — исторически fastembed уже клал систему в 06:00 UTC). **Обратимость:** легко (env-флаг, выключен по умолчанию).

**Примерный diff:**
```bash
# lib/insight-hashes.sh
DREAM_DEDUP_SEMANTIC="${DREAM_DEDUP_SEMANTIC:-0}"
DREAM_DEDUP_SIM_THRESHOLD="${DREAM_DEDUP_SIM_THRESHOLD:-0.88}"

registry_has_hash() {
  local h="$1"
  [[ -f "$INSIGHT_REGISTRY" ]] || return 1
  # ...существующий exact-match как есть...
  if [[ "${DREAM_DEDUP_SEMANTIC}" == "1" && -n "${2:-}" ]]; then
    nice -n 19 ionice -c 3 python3 "$BRAIN_DREAM_REPO/tools/finding-dedup.py" \
      --mode query --registry "$INSIGHT_REGISTRY" \
      --threshold "$DREAM_DEDUP_SIM_THRESHOLD" --text "$2" && return 0
  fi
  return 1
}
```

## Proposal #2: Approval-gate guard на промоушен кандидатов

**Что заметил:** сон 2026-10-30 — «Brain автопромоутит кандидатские ноды без человеческого гейта — паттерн повторяется в SKVO, Travelmart и Marquiz одновременно». Одновременность в трёх доменах говорит о глобальном переключателе, не о доменной особенности. `lib/guards.sh` имеет 5 защит (source-filter, rate-limit, cost-circuit-breaker, depth-counter, kill-switch) для вызовов агентов, но ни одной для действия «кандидат → постоянная нода». `brain-improver.sh` явно декларирует «арм применения никогда не меняет Brain-ноды» — значит автопромоушен идёт из другого скрипта (виден только по коммиту `daf9472 promote: ротация выборки...`), который guards.sh не вызывает вовсе.

**Предложение:** добавить в `lib/guards.sh` функцию `guard_promotion_approval()` — требует файл-маркер явного одобрения (`$GUARD_STATE_DIR/promote/<domain>-approved`) перед флипом статуса кандидата; найти и завести в неё promote-скрипт из коммита `daf9472`, сейчас не защищённый ни одной из 5 защит.

**Обоснование:** закрывает именно «без человеческого гейта», причём на уровне общего guard-контура, а не патчем одного домена — так паттерн не вернётся в четвёртом домене.

**Риск:** средний (нужно сперва найти сам promote-скрипт — его нет в показанном коде, есть только коммит; слепое подключение guard рискует сломать текущую ротацию выборки). **Обратимость:** легко (kill-switch-паттерн уже есть, можно включить permissive-режим с логированием до strict).

## Proposal #3: Валидация commit-ссылок перед записью decision/lesson-нод

**Что заметил:** сон 2026-10-27 — «Decision о фиксе зума в rinatik ссылается на неверный коммит». Это синтез Sonnet'ом commit-хеша в тексте инсайта без проверки, что хеш существует в целевом репо — классическая галлюцинация атрибуции, которая затем попадает в Brain как «факт» (`DREAM_WRITE_NODE=1` путь в `brain-dream.sh`) и будет доверяться другими агентами без переверки.

**Предложение:** перед записью ноды в `DREAM_NODE_ROOT` добавить шаг валидации — извлечь токены вида `[0-9a-f]{7,40}` из синтезированного текста и проверить `git -C <domain_repo> cat-file -e <hash>`; при провале — вырезать конкретную ссылку или выставить `unverified_commit_ref: true` во frontmatter, а не писать неверную цитату тихо.

**Обоснование:** дешёвая проверка (локальный git, без LLM-вызовов), закрывает конкретный класс ошибки синтеза, который уже привёл к неверной ноде в графе.

**Риск:** низкий. **Обратимость:** легко.
