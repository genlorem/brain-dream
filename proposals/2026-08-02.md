## Proposal #1: Дедуп кандидатов ловит только буквальные повторы — тема Marquiz/Балин генерируется заново каждую ночь под новой формулировкой

**Что заметил:** в `~/brain/dreams/.insight-hashes.jsonl` за последние 7 дней 103 записи `domain=marquiz/decision` — почти все это одна и та же мысль («владелец ПО ≠ получатель платежа, ИП Балачкова vs ООО Marquiz») в 15–20+ разных формулировках: «Разрыв между владением ПО и потоком платежей», «Несоответствие IP и потоков платежей», «Marquiz IP vs. Payment Flow», «Противоречие в собственности ПО и финансовом потоке» и т.д. `hit_count` у них у всех = 1 — `content_hash_insight` (`lib/content-hash.sh`) ни разу не признал их дублями, потому что хеширует нормализованный буквальный текст, а не смысл. Заголовки самих снов 4 ночи подряд (26,28,29,30 июля) кружат вокруг той же темы. Это согласуется с кодом `launch_iteration()` (`brain-dream.sh:1206-1305`): кластер `marquiz/decision` выбирается round-robin по `iteration % cluster_count` независимо от того, сколько уникальных (по слабому хешу) кандидатов он уже выдал, а `DREAM_RECENT_WEIGHT_PCT=70-90%` намеренно тянет самые свежие ноды — если свежие ноды в кластере это сплошь про Балина (тема реально активна в жизни), каждый проход по кластеру почти гарантированно рождает «новый» по хешу, но не по сути инсайт. Резкий провал `candidate_count` 30 июля (41 против 420-440 в остальные ночи при том же наборе доменов) — вероятно, ровно этот кластер наконец «выжат насухо» и утаскивает saturation-порог за собой раньше, чем другие домены (govori, skvo, infra) успели получить свою долю проходов.

**Предложение:** в `launch_iteration()` (`brain-dream.sh`, ветка `single`-mode вокруг строк 1276-1285) добавить ночной cap на кластер: bash-ассоциативный массив, считающий кандидатов на `domain_label` из `CANDIDATES_FILE` за текущий прогон; если кластер уже выдал ≥ `DREAM_CLUSTER_NIGHT_CAP` (например 15) кандидатов, сдвигать `first_index` на следующий кластер (до `cluster_count` попыток) вместо того чтобы снова бить по тому же.

**Обоснование:** останавливает трату gemini/sonnet-проходов на переформулировку уже известного факта и высвобождает бюджет для доменов, которые сейчас систематически недополучают внимание (skvo/govori/infra получают в разы меньше кандидатов, чем один под-тип одного домена).

**Риск:** средний — трогает логику отбора кластера, может неожиданно снизить охват реально «горячей» темы, если её стоило продолжать копать. **Обратимость:** легко (новый env-флаг, дефолт 0 = выключено = старое поведение).

## Proposal #2: Находки session-observer (958 нод, ~16% всего registry) физически не могут попасть в promote-пайплайн — фильтр по тегу

**Что заметил:** `agents/session-observer.sh:498` пишет в общий registry с `domain="dreams"` и **пустым `dream_id`** (единственное место в коде с таким вызовом — `brain-dream.sh:1352` всегда передаёт `dream_id`). Эти находки — самокритичные наблюдения о живых Claude Code сессиях, среди них реально ценные: `confidence=1.0` «Claude Code игнорирует явно переданный КОНТЕКСТ НОД при поиске инсайтов», «source_ids ссылаются на ноды, невидимые в отображаемом контексте» и др. (я проверил: в актуальном коде `run_generation_iteration`/`run_sonnet_iteration` оба уже фильтруют `source_ids` по `allowed_ids_json` — то есть это либо уже исправлено, либо баг был в другом месте, и сама находка не документирует, где именно). Ноды пишутся как `finding-*.md` с `source_system: claude-code` (`session-observer.sh:529`), а сам файл честно признаёт: *«Phase 2 hook: promotion to source-of-truth + TG-gate NOT implemented here»* (строка ~503). Я проверил `tools/mined-promote.py:163-179` — единственный акт, который промоутит ноды из `~/brain/dreams/nodes/**/*.md` в боевые домены — жёстко фильтрует `"mined-candidate" not in tags: continue`. `session-observer.sh` не проставляет этот тег (его `tags` — свободный вывод LLM, не гарантирует конкретное значение). Итог: 958 нод накапливаются в `~/brain/dreams/nodes/` мёртвым грузом, ни разу не просканированы на promote.

**Предложение:** в `session-observer.sh` перед записью frontmatter (около строки 539, где формируется `tags: %s`) программно добавить тег `"mined-candidate"` к `c_tags` через `jq`, а не полагаться на то, что модель сама его придумает:
```bash
c_tags=$(printf '%s' "$c_tags" | jq -c '. + ["mined-candidate"] | unique')
```

**Обоснование:** активирует уже существующий promote-пайплайн (`mined-promote.py`, судья с `brain_search`-дедупом, cron 04:40 UTC) для находок session-observer без написания нового кода — закрывает прямо признанный в комментарии Phase-2-gap.

**Риск:** низкий — один тег, влияет только на то, что раньше игнорировалось; `mined-promote.py` уже сам проверяет confidence ≥0.85 и делает dry-run по умолчанию. **Обратимость:** легко (убрать строку).
