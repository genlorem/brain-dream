## Proposal #1: Семантический дедуп инсайтов вместо точного хеша текста

**Что заметил:** инсайт «gena-vps концентрирует критичные секреты SKVO» встретился дважды за 3 ночи — 18.10 как пункт #10 («gena-vps стал точкой концентрации критичных доступов SKVO», перечислены токен Яндекс.Диска, перелогин Instagram, WhatsApp-авторизация), 21.10 — как заголовок всей ночи («gena-vps держит оба критичных секрета SKVO в одной точке»). Формулировка и состав секретов отличаются достаточно, чтобы `content_hash_insight` (lib/content-hash.sh: lowercase + схлопывание пробелов + sha256 по `title|insight`) их не признал дублем — дедуп в lib/insight-hashes.sh сравнивает хеши строго, без учёта смысла. Находка не получила накопления confidence/hit_count, а заново съела слот топ-10 и бюджет синтеза Sonnet.

**Предложение:** в `registry_has_hash` (lib/insight-hashes.sh) добавить вторую, опциональную проверку по эмбеддингам поверх текущего точного совпадения — не вместо него. В репозитории уже есть рабочий эмбеддинг-дедуп (`finding-dedup.py`, fastembed, упомянут в комментарии `orchestrator/session-observer-cron.sh`) — переиспользовать его подход, а не писать новый. Сравнивать новый инсайт только с записями `INSIGHT_REGISTRY` внутри окна `DREAM_DEDUP_WINDOW_DAYS` (уже есть `registry_build_flat` для этого окна — расширить на эмбеддинги), порог косинусной близости ~0.85 → `registry_bump_hit` вместо `registry_append`.

**Обоснование:** без этого правки формулировки (а они естественны при разных Gemini/Sonnet проходах) полностью обходят дедуп — система не умеет отличать «та же проблема другими словами» от «новая проблема». Один и тот же факт будет регулярно всплывать как «свежий» топ-инсайт, искажая ощущение новизны и тратя синтез-бюджет повторно.

**Риск:** средний — эмбеддинг-вызов в hot path `registry_has_hash`, а fastembed уже один раз клал хост (load 22-25 на 06:00 UTC, упомянуто в session-observer-cron.sh) из-за перезакладки всего корпуса эмбеддингов на каждый вызов. Обязательно кэшировать эмбеддинги по hash в самом registry (одно поле `embedding` в JSONL), считать новый только для входящего кандидата, сравнивать только с окном 14 дней, а не всей историей. **Обратимость:** легко — флаг `DREAM_SEMANTIC_DEDUP=0` отключает, точный хеш остаётся основным путём.

**Примерный diff:**
```bash
# lib/insight-hashes.sh
DREAM_SEMANTIC_DEDUP="${DREAM_SEMANTIC_DEDUP:-0}"   # дефолт выкл до обкатки

registry_has_similar() {
  local text="$1"
  [[ "$DREAM_SEMANTIC_DEDUP" == "1" ]] || return 1
  registry_build_flat   # уже строит окно 14 дней
  python3 "$BRAIN_DREAM_REPO/tools/embed-dedup.py" \
    --query "$text" --registry "$INSIGHT_REGISTRY" --threshold 0.85
}
```

## Proposal #2: Телеметрия «кандидатов на вызов» для диагностики проседаний

**Что заметил:** ночь 18.10 — 61 вызов Sonnet (столько же, сколько 19/23/24.10), но только 51 кандидат против 140-152 в обычные ночи, и при этом цена $59.11 — на 50-60% дороже типичной ночи ($36-39). Это даёт ~$1.16 за кандидат против ~$0.26 в нормальную ночь — разница почти в 4.5 раза, и явно не похожа на обрыв по аккаунту (это другой, уже устранённый случай 22.10, где упал именно счётчик вызовов до 22). Причину по текущим полям frontmatter (`sonnet_calls`, `candidate_count`, `cost`) восстановить невозможно — неизвестно, сколько кандидатов срезал `style_gate.py`, сколько — точный дедуп, или просто ответы были длиннее и малопродуктивнее.

**Предложение:** в brain-dream.sh там, где кандидат проходит через `style_gate.py` и через `registry_has_hash` перед записью в `CANDIDATES_FILE`, считать и писать в frontmatter отчёта два новых поля: `style_gate_rejected_count` и `dedup_rejected_count` (по аналогии с уже существующими `candidate_count`, `sonnet_calls`). В `dream-night-check.sh` добавить сравнение `candidate_count / sonnet_calls` с скользящей медианой последних N ночей (взять из уже читаемого `brain-dream.log`) и слать алерт через существующий `brain-act-alert.sh`, если отношение упало более чем в 2 раза.

**Обоснование:** задание прямо называет «мало кандидатов» первым кандидатом на улучшение — он уже произошёл (18.10) и прошёл незамеченным, потому что метаданные не разделяют «мало кандидатов из-за насыщения» (ожидаемо, не баг) от «мало кандидатов при аномально высокой цене» (баг или деградация промпта/гейта). Без этого разделения каждое повторение будет требовать ручной археологии по логам, как сейчас.

**Риск:** низкий — чисто аддитивные счётчики и алерт, не меняет логику генерации или дедупа. **Обратимость:** легко — новые поля опциональны, алерт убирается удалением одной проверки.

## Proposal #3: Алерт на хроническую нулевую выработку Gemini

**Что заметил:** во всех 7 снах недели (18-24.10) `gemini_passes: 0` и `gemini_cost_usd: 0` — без единого исключения. `DREAM_SONNET_FALLBACK_RUNS=60` в brain-dream.sh совпадает ровно с наблюдаемым `sonnet_calls` в обычные ночи (59-61) — то есть каждую ночь срабатывает запасной путь на Sonnet, а не задуманное сравнение Gemini/Sonnet. Это согласуется с известной остановкой Code Assist OAuth-лицензии с 01.09.2026 (заметка в CLAUDE.md про `~/bin/gemini`), но для самого brain-dream (`DREAM_GEMINI_BACKEND=cli` в dream-nightly.sh) этот факт не зафиксирован отдельно и не алертится — систему просто тихо несёт на fallback-режиме уже как минимум неделю, а по факту похоже дольше.

**Предложение:** завести в `~/brain/dreams/.gemini-health.json` счётчик подряд идущих ночей с `gemini_passes=0` (по аналогии с `DREAM_TRIGGER_STATE` в dream-should-run.sh) и в brain-dream.sh после Gemini-фазы писать в него; при достижении порога (например, 5 ночей подряд) слать через `~/bin/brain-act-alert.sh` сообщение «Gemini не работает N ночей — проверить CLI-бэкенд или явно отключить primary-фазу».

**Обоснование:** дизайн с двумя моделями (сравнение Gemini/Sonnet, денежный лимит $0.50 на Gemini) сейчас не исполняется ни одну ночь из наблюдаемых — весь расход идёт в долю сессионной подписки Sonnet (30% от 200 вызовов каждую ночь), а не в заложенный Gemini-бюджет. Без алерта это состояние может длиться месяцами незамеченным, а решение «чинить Gemini» или «official убрать primary-фазу и оставить только Sonnet» никогда не будет принято, потому что никто не увидит сигнал для его принятия.

**Риск:** низкий — только чтение состояния и алерт, не трогает сам Gemini/Sonnet-пайплайн. **Обратимость:** легко — удаление state-файла и проверки откатывает поведение полностью.
