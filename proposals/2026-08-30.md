## Proposal #1: Gemini-фаза мертва минимум неделю, и это невидимо без ручного кросс-сравнения снов

**Что заметил:** Все 7 снов подряд (08-23…08-29) показывают `gemini_passes: 0` и `gemini_cost_usd: 0` — это не заметно из одного сна (выглядит как «сегодня не понадобился»), только сравнением всех фронтматтеров разом. Проверил код: `orchestrator/brain-dream.sh:2323-2327` — при `! gemini_available()` ставится `GEMINI_UNAVAILABLE=1`, `STOP_REASON="gemini_unavailable"`, и весь синтез молча уходит на Sonnet-фолбэк. Логи подтверждают: `stage=done gemini_launched=0 ... sonnet_launched=60` за 08-29. `~/.config/gemini/` на этом хосте отсутствует — при дефолтном `DREAM_GEMINI_BACKEND=api` (`gemini.sh:443` → `require_api_key`) это и есть причина. Единственный Telegram-алерт (`brain-dream.sh:2447`) срабатывает только если **и** Sonnet-фолбэк дал 0 кандидатов — порог намного выше, чем «неделя на одном фолбэке», поэтому алерт никогда не сработал.

**Предложение:**
1. Добавить в frontmatter (`brain-dream.sh`, блок печати ~строка 1845, рядом с `gemini_passes`) явное поле `engine_status: <gemini_ok|gemini_unavailable>` из уже существующей переменной `GEMINI_UNAVAILABLE`/`STOP_REASON` — не гадать по нулю.
2. Отдельный (не «всё упало») Telegram/лог-алерт при N-м подряд `gemini_unavailable` (например, ≥3 ночи подряд) — сигнал «фолбэк стал постоянным режимом», а не «сон пуст».

**Обоснование:** Это ровно тот случай, который задание просит ловить первым («что-то очевидно ломается»). Прямое следствие: система неделю жгла ~30%/ночь сессионного лимита подписки Sonnet вместо дешёвого Gemini API — незапланированный расход, о котором никто не узнал бы без этого разбора.

**Риск:** низкий. **Обратимость:** легко (чисто аддитивные поля/алерт, генерацию не трогает).

## Proposal #2: Чинить Gemini-фазу через уже существующий gemini-proxy, а не через мёртвый прямой путь

**Что заметил:** Root cause #1 — `gemini.sh` дефолтит на `GEMINI_BACKEND=api`, требующий `~/.config/gemini/config.env`, которого на этом хосте нет (владелец сам зафиксировал в CLAUDE.md: «на gena-vps его нет», плюс личный OAuth CLI `gemini` мёртв с 2026-06-18). У владельца уже есть рабочий обходной путь — тайлнет-мост `gemini-proxy` (`~/bin/gemini -p`, `askGeminiProxy`), которым в session-manager уже пользуются вместо прямого ключа.

**Предложение:** В `orchestrator/gemini.sh` добавить третий backend `proxy` (рядом с `api`/`cli`, переключение уже есть на строках 357/422-423): при `GEMINI_BACKEND=proxy` дергать `~/bin/gemini -p "<prompt>"` вместо REST/CLI. В `brain-dream.sh` выставить `DREAM_GEMINI_BACKEND=proxy` на хостах без `~/.config/gemini/config.env`. Учесть ограничение моста (нет `systemInstruction`/`responseMimeType`, JSON приходит в ```json-обёртке — снимать) и щедрый таймаут (~120с).

**Обоснование:** Восстанавливает дешёвую генерацию вместо постоянного пожирания Sonnet-сессии, устраняет первопричину #1, а не только видимость проблемы.

**Риск:** средний (новый код-путь, другой формат ответа моста нужно адаптировать). **Обратимость:** легко (env-флаг, старые backend'ы остаются).

## Proposal #3: Точный dedup инсайтов пропускает пересказанные повторы — сам механизм ловит ровно ту болезнь, которую описывает

**Что заметил:** Топ-10 сна 08-25/08-26 пункт #6 описывает баг pattern-mining-гейта: три lesson-ноды про один и тот же рецидив без supersede-связи. Заголовок сна 08-28 — «Pattern-mining: **4-й** рецидив одного и того же архитектурного бага без консолидирующей ноды» — то есть спустя пару ночей всплыла та же тема как якобы новый топ-инсайт. `lib/content-hash.sh` хеширует `title+insight` только после lowercase/схлопывания пробелов — точное совпадение строки. Разные формулировки одного и того же архитектурного бага (разные конкретные lesson-id: ssh-ssh, scp-ssh-brainadd, git-stash-pop, +4-й) дают разный хеш и обходят `registry_has_hash` (`lib/insight-hashes.sh`).

**Предложение:** В `lib/insight-hashes.sh` добавить `registry_has_similar_title()` — сравнение по пересечению значимых слов (≥3 общих токена длиной ≥4, тот же `domain`) среди записей в окне `DREAM_DEDUP_WINDOW_DAYS`. Не блокировать кандидата, а пометить (`[⚠ похоже на: <старый title>]`) перед записью в `CANDIDATES_FILE` — решение о слиянии остаётся за синтезом/человеком.

**Обоснование:** Задание прямо называет «повторяются темы» первым кандидатом на починку — вот конкретный, дважды подтверждённый пример, и текущий dedup именно такие случаи пропускает.

**Риск:** низкий (аддитивная пометка, не блокирует новые кандидаты). **Обратимость:** легко.
